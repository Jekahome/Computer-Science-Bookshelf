# OS


## Что вообще изучает курс по операционным системам?

Если открыть любой университетский курс (MIT, Berkeley, Stanford), то он обычно строится примерно так:
* Что такое процесс.
* Что такое поток.
* Планировщик.
* Контекстное переключение.
* Виртуальная память.
* Системные вызовы.
* Файловые системы.
* Драйверы устройств.
* IPC.
* Синхронизация.

Заметь — почти нигде нет того что связано только с платформой IBM PC (x86) - GDT или BIOS/UEFI. Это потому, что это архитектурные детали, а не фундаментальные идеи ОС.

Только для x86, большая часть времени уйдёт на ее особенности: BIOS/UEFI; GRUB; GDT; IDT; APIC; legacy-устройства; режимы процессора.

<br>
<details>
<summary><b>Почему OS FreeRTOS тоже не лучший вариант</b></summary>

FreeRTOS учит устройству **встроенных** систем, а не устройству **ОС общего назначения**.

FreeRTOS — это RTOS (операционная система реального времени).

Она отлично показывает:
* задачи;
* планировщик;
* очереди;
* семафоры;
* мьютексы.

Но почти не показывает:
* процессы;
* виртуальную память;
* файловые системы;
* загрузку программ;
* пользовательский режим;
* системные вызовы в классическом смысле.

> ARM-микроконтроллер STM32F303 - это мощный ARM-микроконтроллер без MMU. На нём можно запускать лишь RTOS (операционные системы реального времени) вроде FreeRTOS или NuttX, но не Linux или Windows. Это хороший выбор для изучения встраиваемых систем, но не ОС общего назначения.

## Варианты практики разработки OS
* тестировать ОС на виртуальном процессоре RISC-V в симуляторе Digital (много еще не реализованно)
* тестировать ОС на виртуальном процессоре RISC-V в эмуляторе QEMU
* тестировать ОС на реальном RISC-V SBC: StarFive VisionFive 2 или Milk-V Mars (нет в наличии)
* тестировать ОС на реальном Raspberry Pi 3/4 (есть в наличии)


Raspberry Pi — очень хорошая платформа для изучения ОС, но потребует освоения новой архитектуры ARM.

Raspberry Pi (модели 4/5): Это настоящий компьютер с ARM-процессором, поддержкой виртуальной памяти (MMU) и полноценной архитектурой. На нём вы можете писать свою ОС "с нуля" (bare metal), работая непосредственно с железом через HDMI, USB и другие интерфейсы. Существуют готовые туториалы по созданию ОС для Raspberry Pi 4. 
 
Если сейчас перейти на Raspberry Pi, то одновременно придётся изучать:
* ARM ISA;
* систему исключений ARM;
* загрузку ARM;
* документацию BCM2711 (или другого SoC).

Лучше перенести знания о RISC-V на реальное RISC-V железо, чем начинать изучение ARM только потому, что Raspberry Pi есть в наличии. Это позволит сосредоточиться на механизмах операционных систем, а не снова тратить много времени на освоение новой ISA.

> [!INFO]
> Начать с виртуального тестирования в эмуляторе QEMU под RISC-V (и Raspberry Pi ?).
> Когда появится RISC-V SBC — портировать архитектурный слой и драйверы на реальное железо.


Обе платы RISC-V SBC, и StarFive VisionFive 2, и Milk-V Mars, построены на одном и том же процессоре StarFive JH7110. Это 64-битный четырёхъядерный RISC-V процессор, который работает на частоте до 1.5 ГГц. Это один из первых массовых RISC-V процессоров, способных запускать полноценные Linux-системы. Процессор поддерживает современные интерфейсы: PCIe 2.0, USB 3.0, Gigabit Ethernet и HDMI с разрешением до 4K. Встроенный 3D-графический ускоритель (IMG BXE-4-32 MC1) и аппаратный блок для кодирования/декодирования видео, что редкость для RISC-V плат.

StarFive и Milk-V (на процессоре JH7110) — это попытка создать конкурента Raspberry Pi, но архитектурно и по производительности они уступают даже Raspberry Pi 4, не говоря уже о Pi 5.

*Или писать переносимую ОС. Первая реализация архитектурного слоя будет для ARM64 на Raspberry Pi. Позже добавлю второй слой для RISC-V.*

ОС не является полностью независимой от процессора, но её можно спроектировать так, чтобы зависимая от архитектуры часть была небольшой и хорошо изолированной.

Типичная структура выглядит примерно так:
```
+--------------------------------------+
| Пользовательские программы           |
+--------------------------------------+
| libc                                 |
+--------------------------------------+
| Syscall API                          |
+--------------------------------------+
| VFS | Scheduler | VM | IPC | Network |
+--------------------------------------+
| HAL / Arch Interface                 |
+--------------------------------------+
| ARM64 | RISC-V | x86                 |
+--------------------------------------+
| Конкретное оборудование              |
+--------------------------------------+
```


Верхние уровни вообще не знают, какой процессор используется.


#### Что можно написать уже сейчас на Raspberry Pi

Всё это потом почти без изменений перенесётся на RISC-V.
 
* менеджер физических страниц памяти;
* kmalloc;
* планировщик;
* модель процессов;
* системные вызовы;
* VFS;
* файловую систему;
* ELF loader;
* shell;
* драйверную модель;
* таймеры (через абстракцию);
* синхронизацию (mutex, spinlock и т.д.).
 

#### Что придётся переписать

То есть всё, что связано с:

* загрузкой процессора;
* переключением контекста;
* обработкой исключений;
* таблицами страниц;
* регистрами процессора;
* контроллером прерываний.

Вот эту часть:
```
arch/
    arm64/
        boot.S
        trap.S
        context.S
        mmu.rs
        timer.rs
        uart.rs

    riscv64/
        boot.S
        trap.S
        context.S
        mmu.rs
        timer.rs
        uart.rs
```

Если начать с Raspberry Pi, **с самого начала проектируйте архитектурный слой**, а не код напрямую под ARM.

Например, не так: `arm64::enable_interrupts();` а так: `arch::enable_interrupts();`

## Структура операционной системы: Модульное ядро со слоями ответственности.


 Структуры операционной системы по книге Таненбаум Э. - Современные операционные системы. 4-е изд. 2015
* Монолитные системы
* Многоуровневые системы
* Микроядра
* Клиент-серверная модель
* Виртуальные машины
* Экзоядра

Экзоядра какую структуру мне выбрать?

Я бы выбрал модульное монолитное ядро.

Именно так сделаны:
* Linux;
* FreeBSD;
* XNU (ядро macOS хоть и содержит микроядерные элементы, но по сути тоже гибрид).

То есть логически ядро разделено на подсистемы, но они работают в одном адресном пространстве.
Каждая подсистема имеет чёткий интерфейс.

Но работают они внутри одного ядра.

Модульное ядро со слоями ответственности.

```
                 User programs
                      │
                      ▼
                 System calls
                      │
                      ▼
        +-----------------------------+
        | Process | VFS | Net | IPC   |
        +-----------------------------+
        | MM | Scheduler | Drivers    |
        +-----------------------------+
        | Architecture Abstraction    |
        +-----------------------------+
        | ARM64 | RISC-V              |
        +-----------------------------+
```

Если сделать хорошее разделение на модули:
* можно независимо писать планировщик;
* независимо менять файловую систему;
* независимо добавлять драйверы;
* независимо переносить на RISC-V.

Если бы мы вместе проектировали твою ОС с нуля, я бы заложил такую архитектуру:
* Модульное монолитное ядро — всё ядро работает в одном адресном пространстве.
* Многоуровневая организация внутри ядра — подсистемы взаимодействуют через чёткие интерфейсы, а не напрямую.
* Отдельный слой arch/ для ARM64 и RISC-V, чтобы переносимость была предусмотрена с самого начала.
* Минимальные зависимости между модулями, чтобы позже можно было заменить или переработать отдельные части без переписывания всего ядра.

## QEMU (Quick EMUlator) программа для эмуляции и виртуализации железа

QEMU позволяет запустить операционную систему для одного процессора (например, RISC-V или ARM) на абсолютно другом процессоре (например, на вашем x86-64 ноутбуке).

QEMU делает две ключевые вещи:
* Эмуляция (Machine Emulation): Он перехватывает машинные коды программы и переводит их "на лету" в понятные для вашего текущего процессора команды (это называется динамической трансляцией). Благодаря этому вы можете запустить код, написанный для железки, которой у вас нет в руках.
* Виртуализация (Virtualization): Если ваш процессор и хост-система совместимы с гостевыми (например, вы ставите Linux на Linux), QEMU может работать в режиме KVM (Kernel-based Virtual Machine). В этом случае он не эмулирует процессор, а просто "прокидывает" команды напрямую в железо, давая почти нативную производительность.

QEMU может работать в двух режимах:
* Пользовательский режим (User Mode): Эмулирует только процессор и запускает отдельную программу, как обычный процесс в вашей системе. Быстро и удобно для отладки.
* Системный режим (System Mode): Эмулирует целый компьютер целиком — со своим процессором, памятью, видеокартой, сетевыми картами и дисками. Можно загрузить полноценную ОС (например, запустить Windows XP на ARM-ноутбуке).

Для машины virt, уже дают практически полноценный компьютер.

```
                 CPU (RV64GC)
                      │
          Supervisor Mode
                      │
             Virtual Memory
                      │
        --------------------------
        │        RAM             │
        --------------------------
          │      │        │
        UART   PLIC    VirtIO
          │               │
       Console      Disk / Net
```

## OpenSBI

OpenSBI — это не операционная система и не загрузчик в привычном смысле. Это реализация интерфейса SBI (Supervisor Binary Interface).

На обычном ПК x86 загрузка выглядит так:
```
Питание
   │
   ▼
BIOS/UEFI
   │
   ▼
GRUB
   │
   ▼
Linux
```

На RISC-V обычно так:
```
Питание
   │
   ▼
Boot ROM
   │
   ▼
OpenSBI
   │
   ▼
твоя ОС
```

На большинстве современных RISC-V систем ядро ОС не работает в Machine Mode, а запускается в Supervisor Mode. 
Поэтому возникает вопрос: Кто тогда выполняет привилегированные операции?

В RISC-V есть несколько уровней привилегий:
* M-mode — самый привилегированный режим. Управляет таймерами, межпроцессорными прерываниями и другими низкоуровневыми вещами.
* S-mode — здесь обычно работает ядро Linux или другой ОС.
* U-mode — пользовательские приложения.

```
Machine Mode (M)
        │
        ▼
Supervisor Mode (S)
        │
        ▼
User Mode (U)
```

Например, ядро хочет перезагрузить компьютер:
```
Kernel (S-mode)
       │
       ▼
SBI call
       │
       ▼
OpenSBI (M-mode)
       │
       ▼
Hardware
```
То есть OpenSBI похож на очень маленькую "прошивку", которая предоставляет сервисы ядру.

А четвертый уровень User Space (на уровене kernel,arch,platform) появится значительно позже, когда будут реализованы:
* виртуальную память;
* процессы;
* системные вызовы (ecall);
* загрузку ELF.

Уровень **arch**  то, что связано только с процессором и требует знания ISA:
* переключение контекста;
* обработка trap;
* системные вызовы;
* MMU;
* таблицы страниц;
* TLB;
* чтение/запись CSR;
* управление прерываниями на уровне CPU.

```
arch/
    riscv64/

        boot.S

        context.S

        trap.S

        csr.rs

        paging.rs

        cpu.rs
```

Уровень **platform** то, что связано только с конкретной платой:
* UART;
* карта памяти;
* контроллер прерываний (например, PLIC или GIC);
* таймеры;
* GPIO;
* VirtIO;
* SD-контроллер.


Уровень **kernel** содкржит логику операционной системы, которая не зависит ни от процессора, ни от конкретного оборудования.
arch — это не часть kernel, а подсистема ядра. Аналогично drivers

```

                    |     User Space       |  (появится позже)

                              │

                +---------------------------+
                |        Hardware           |
                +---------------------------+
```
